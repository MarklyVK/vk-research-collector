# Архитектура хранения данных

Первый этап использует PostgreSQL как единственный источник истины для кандидатов,
очереди и прогресса. Python работает через SQLAlchemy 2.x и `asyncpg`; сессии не
передаются между конкурентными задачами.

## Схема

- `group_candidates` — одна строка на положительный VK ID, актуальные публичные поля
  группы и результат классификации. Сырые ответы VK не сохраняются.
- `search_keywords` — нормализованные ключи и их предметные области.
- `search_runs` — история ручных запусков.
- `search_run_keywords` — статус и следующий offset каждого ключа в запуске. Эта
  строка обновляется транзакционно после сохранения страницы и позволяет продолжить
  работу после перезапуска.
- `group_keyword_matches` — уникальная пара группы и ключа; повторный поиск обновляет
  `last_matched_at`, но не создаёт дубль.
- `classification_batches` и `classification_batch_items` — фиксированный снимок
  экспорта. Триггер запрещает изменение и удаление элементов готового пакета.
- `group_labels` — уникальные классификационные метки группы.
- `collection_jobs` — общая возобновляемая очередь будущих задач. На первом этапе
  основной сбор не выполняется.

Все даты имеют PostgreSQL-тип `timestamptz`; контейнер и база должны работать в UTC.
Уникальность VK ID, совпадений, элементов пакета и меток обеспечена ограничениями
PostgreSQL, поэтому корректность не зависит от числа процессов.

## Транзакции классификации

Импорт должен открыть одну `AsyncSession.begin()`, заблокировать пакет и его группы
через `SELECT ... FOR UPDATE`, полностью проверить входной документ, затем обновить
статусы и метки. Любое исключение откатывает весь импорт. Повторный импорт пакета,
у которого задан `imported_at`, должен быть отклонён.

## Read-only роль

Пароль `vk_reader` никогда не включается в миграцию. Инфраструктурный bootstrap
создаёт роль из `POSTGRES_READER_PASSWORD`; начальная миграция выдаёт ей только
`CONNECT`, `USAGE` и `SELECT`, если роль уже существует. Роль приложения выполняет
миграции и запись.
