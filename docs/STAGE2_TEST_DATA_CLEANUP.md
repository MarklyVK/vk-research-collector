# Очистка тестовых данных перед вторым этапом

## Идентификация

Integration-тест `test_export_and_minimal_import_are_transactional` создавал по две
группы с `screen_name = test_<vk_id>`, keyword `доставка-<uuid>` и отдельным batch.
Совпадение всех трёх признаков обнаружило ровно 12 строк: шесть approved и шесть
rejected.

| `2026-07-27-68d893098fd1` | 5130647955 | 4225948189 |
| `2026-07-27-3887787ba0b4` | 1768176442 | 2956777313 |

| `2026-07-27-2ae94c4b14ff` | 4926873632 | 2826163453 |

Все шесть batch содержат только указанные пары. Ни один из 12 VK ID не встречается в
377 JSON-файлах `exports/classification-final`, содержащих 37 407 уникальных VK ID.
До очистки база показывала `approved=12266`, `rejected=25153`, `pending=0`.

## Безопасная процедура

Перед очисткой создаётся `pg_dump -Fc` и проверяется `pg_restore --list`. В одной
транзакции повторно проверяются признаки и количество строк, временно отключается
immutable-trigger batch items, удаляются только подтверждённые batch/items/groups,
неиспользуемые test keywords и их search runs, затем trigger включается до commit.
После операции проверяются orphan records и целевые счётчики 12 260 / 25 147 / 0.

Integration-тест переводится на внешнюю rollback-транзакцию, поэтому его внутренние
`commit` больше не загрязняют общую базу.
