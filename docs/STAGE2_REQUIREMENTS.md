# Требования второго этапа

## Цель и границы

Второй этап собирает через официальный VK API только публичные данные по
`group_candidates.classification_status = approved`. Источником групп остаётся таблица
`group_candidates`; rejected, pending и подтверждённые тестовые группы не планируются.

Собираются: актуальные метаданные групп, до 100 последних постов, нормализованные
метаданные вложений без бинарных файлов, публичные участники с безопасным начальным
лимитом 200, минимальные публичные профили и, только при отдельном capacity gate,
публичные подписки пользователей на сообщества.

Не собираются личные сообщения, контакты, адреса, фотографии и другие бинарные файлы,
родственники, взгляды и иные чувствительные поля. HTML scraping, обход закрытых профилей,
сохранение сырых VK-ответов и токенов запрещены. Отдельный REST API, web UI, LLM,
векторизация и внешний брокер очередей не входят в этап.

## Включение и пропуск

- В run включаются только approved-группы, существующие на момент планирования.
- Pilot выбирается детерминированно с seed `20260728`: по 10 групп каждой из четырёх меток и до
  пяти multi-label групп.
- Закрытая, удалённая или недоступная сущность получает конечный `skipped` с причиной.
- Временная ошибка получает ограниченный retry; отсутствие всех токенов ставит run на
  паузу. Недоступный официальный метод не заменяется scraping и отмечается `unsupported`.
- Профиль обновляется только после истечения TTL. Подписки по умолчанию выключены.

## Идемпотентность и возобновление

Plan-key включает scopes и все лимиты, влияющие на ёмкость; capacity report применим
только к full run с идентичной конфигурацией. Внутри run задание уникально по
`(run, job_type, entity_type, entity_id)`. Worker захватывает задания
через `FOR UPDATE SKIP LOCKED`; просроченная lease восстанавливается. Каждая страница
сохраняется одной транзакцией вместе с checkpoint. Upsert и ограничения PostgreSQL не
дают создать дубли при restart или полном повторном запуске. Успешные jobs повторно не
выполняются без явного нового run.

Расширение `food_service` не дописывает jobs в основной run. Incremental planner
выбирает только approved-группы вне snapshot указанного baseline run, дедуплицирует
multi-label группы, исключает уже completed jobs соответствующего типа и требует
успешный audit summary с seed `20260730`. В configuration фиксируются
`reason=food_service_increment` и `source=food_service_expansion`.

Участники и подписки имеют snapshot semantics: отсутствующие связи помечаются
неактуальными только после полного, не ограниченного и успешно завершённого прохода.

## Завершение

Техническая готовность требует миграций, unit/integration/smoke-тестов, Docker/CI,
resume- и privacy-проверок. Полная готовность дополнительно требует реального pilot,
измеренного capacity estimate, разрешающего gate, backup и безопасного основного run.
Если внешний VK API или токены недоступны, код остаётся готовым, а run — возобновляемо
приостановленным с точной причиной.

## Endpoint-aware обогащение пользователей и сообществ

Явное расширение этапа добавляет отдельный, выключенный по умолчанию контур публичных
подписок пользователей. Пул токенов учитывает точное имя VK API method: код 6 создаёт
короткий глобальный cooldown, коды 9 и 29 блокируют только пару
`token_fingerprint + method`, а ошибки авторизации 5/27/28 отключают токен целиком.
Состояние rate limit хранится в PostgreSQL без исходных токенов и переживает restart.

Worker выбирает задания weighted round-robin между типами и пропускает временно
недоступные методы. Ожидание method limit не расходует попытку задания; если временно
недоступны все нужные методы, run получает `waiting_method_limit` и `next_wakeup_at`.
После `next_probe_at` одна проба резервируется транзакционно; `blocked_until` остаётся
долгим пределом. Ограничения нескольких разных methods в настраиваемом окне дают
сохраняемый короткий global cooldown, но повторы одного method не эскалируют.

Отдельный planner детерминированно выбирает существующих доступных `vk_users` из
membership approved-групп независимо от TTL профиля. `groups.get` вызывается с
`extended=1`; по умолчанию сохраняется до 50 сообществ пользователя, разрешённое
настраиваемое значение — 100. Метаданные сохраняются в канонический реестр
`vk_communities`, не создавая `group_candidates`. Усечённый snapshot не деактивирует
старые связи.

Для каждого уникального доступного сообщества создаётся не более одного задания
`collect_subscription_group_posts` на run. Оно сохраняет до 20 последних постов и
нормализованные метаданные вложений без binary/raw JSON. Оба новых scope имеют
независимые pilot/capacity gates и до их прохождения выключены.

Gate A, Gate B и два production scope всегда используют отдельные immutable run.
Разрешающий JSON report содержит schema version, run ID, UTC-время, точные limits,
configuration hash, measured/projected значения, лимит 7 GiB и
`production_allowed=true`. Отсутствующий, повреждённый, устаревший или несовпадающий
report блокирует run до чтения токенов и claim задания.
